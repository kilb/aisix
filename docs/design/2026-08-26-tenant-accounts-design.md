# 自助租户账户与预付额度 — 设计

**状态**：待评审
**日期**：2026-08-26

## 1. 要解决什么

让外部客户自助注册、拿到额度后自助生成 API 密钥、只看得到自己的用量；
管理端能看到注册用户并分配额度。额度是**预付**的：先充值或由管理员发放，
有余额才能调用，余额耗尽即停。

明确不做的：把网关变成一个计费系统。网关只回答"这个 scope 还能不能花钱"，
钱是什么、谁欠谁、发票怎么开，全在网关之外。

## 2. 现状（已核实，附出处）

写这一节是因为直觉与事实差得很远：这套东西**已经存在的比看起来多**，
下一个动手的人不该再摸一遍。

### 已经具备，不需要新建

| 事实 | 出处 |
|---|---|
| `ApiKey` 已带 `user_id` / `team_id` / `user_name` / `expires_at` / `disabled` | `crates/aisix-core/src/models/apikey.rs:45–57,130,136` |
| `disabled` 在鉴权处真的拒绝请求，返回 `key_disabled` | `crates/aisix-proxy/src/auth.rs:191–199` |
| 限流策略已有 `Member` / `Team` / `TeamMember` 作用域 | `crates/aisix-core/src/models/rate_limit_policy.rs:48` |
| Prometheus 指标已按 `user_id` 打标 | `crates/aisix-obs/src/metrics.rs:1460,1667,1682` |
| `allowed_models` 可限制某密钥能用哪些模型 | `crates/aisix-core/src/models/apikey.rs:35` |

**结论**：本设计要的"每用户计量隔离"，在数据面已经成立。

### 已经具备，但不是本设计要的东西

OIDC / JWT 入站鉴权存在（`models/oidc_provider.rs`、`claim_mapping.rs`），
但它把外部身份**绑到运维已建好的密钥上**——源码原话：*external identities
never widen access beyond a key an operator explicitly created*。它不创建
密钥，因此不能用来实现自助注册。

### 缺口（本设计要填的）

1. **没有 User 这个实体**。`user_id` 只是一个自由字符串，没有记录、没有凭据、
   没有邮箱、没有余额。
2. **控制台是一个共享口令**（`CONSOLE_PASSWORD_HASH`），登进来即全权管理员，
   没有任何"只能看自己的"边界。
3. **预付余额没有对应机制**。`max_spend_micro_usd` 被投影成 `tpm/tph/tpd`
   （`crates/aisix-proxy/src/quota.rs:437–446`），复用的是 token 的**固定窗口**
   计数器；窗口滚动即刷新（`crates/aisix-ratelimit/src/store/local.rs:348`
   的测试注释："The window rolls and the budget is fresh again"）。
   充 $10 设成 `window: day`，用户是**每天**拿 $10。
4. **Admin API 只读**。`crates/aisix-admin/src/lib.rs` 中全部为 `get(...)`，
   没有任何 POST/PUT/DELETE。
5. **密钥落地走整份 YAML 重写**。控制台 `api_mint_key` 只生成明文与散列
   （`crates/aisix-console/src/main.rs:687`），写入走整文件保存 + 全文件版本
   校验。N 个用户并发铸密钥会持续撞 409，文件亦无限膨胀。
6. **`/api/metrics` 接受任意 PromQL**，仅要求指标名以 `aisix_` 开头
   （`crates/aisix-console/src/main.rs:294,344`）。单管理员下无害；多租户下
   任一用户可查询全体用户的花费，是跨租户泄漏。

## 3. 三条前提

这三条不是风险登记，是**设计据以成立的事实**，改动其中任何一条都要重审本文。

### 3.1 今天没有精确的耗用记录

三个候选来源没有一个精确：

- **usage events**：故意做成有损的。`try_emit` 在队列满时**静默丢弃**以避免
  回压热路径（`crates/aisix-obs/src/usage.rs:630–650`），批量契约 5s / 100 条。
  丢弃有计数（`aisix_usage_event_drops_total{reason}`），但**金额不可恢复**，
  且丢弃恰好发生在负载最高、钱流最快时。
- **Prometheus counter**：采样式。`increase()` 能正确处理网关重启导致的
  counter 重置，但抓取间隙内的增量会丢。
- **RateStore 的 `spend:` 桶**：网关**据以拒绝**的数，最权威——但按窗口重置，
  且是内部结构。

本设计因此**不把账建在遥测上**（见 §4.3）——但该方案依赖三期的累计闸，
一期在它到位之前只能退而读 Prometheus 并接受漂移（见 §7）。

### 3.2 超支由速率反推，不由周期控制

```
超支 ≈ 单用户峰值消费速率 × 检测周期 + 在途请求成本
```

周期只能尽力而为；**速率在准入时精确可控**（`concurrency` / `rpm` /
`allowed_models` 都在 `acquire` 时计数）。因此额度档位的定义顺序是：
先定"每用户最多愿意吃多少超支"，再由它反推速率上限。

一个用户开 4 并发、挑贵模型塞长上下文，单次约 $0.5、10 秒返回 ≈ $0.2/s；
15 秒周期下超支约 $3。并发压到 1、模型白名单只留便宜的，同周期下降到几分钱。

### 3.3 计费服务永不在热路径上

网关**不得**在请求路径上回调计费服务。那是一次新的网络跳，去往一个有自己
数据库和自己可用性的服务：延迟加得实在，更糟的是网关可用性被计费系统绑架，
计费一挂网关就挂。

额度只能通过**配置**下推（与其它配置同一条路），网关在请求时对计费系统零依赖。

## 4. 架构：闸与账本分离

| | 住在哪 | 管什么 | 是否知道"钱" |
|---|---|---|---|
| **闸** | 网关 | 一个数：该 scope 还剩多少 micro-USD，到零即拒 | 否。只知道"还剩 N，扣" |
| **账本** | 门户数据库 | 充值、发放、扣减、发票、退款、争议、历史 | 是。全部业务语义在此 |

耦合面只有两个数字：**往下推「剩余额度」**，**往上读「还剩多少」**。

### 4.1 闸：网关侧的累计扣减额度

新增一种**不重置的累计扣减**计数器：给定授予总额，随消费单调递减，
**不随窗口滚动刷新**。与现有 `max_spend_micro_usd`（窗口型）并存，互不替代——
窗口型仍然是"每天最多花多少"的正确工具，本机制是"总共还剩多少"。

**热路径代价**：`reserve_layers` 的各层是顺序 `.await`
（`crates/aisix-proxy/src/quota.rs:448–511`），`RateStore::acquire` 按桶
（`crates/aisix-ratelimit/src/store/mod.rs:108–125`）。因此：

- **搭在已有的 member 桶上**（用户本就有一条 `scope: member` 策略时）→ 零新增往返
- **独立成一层** → +1 次串行往返

量级：`LocalStore` 是一把 `parking_lot::Mutex`（亚微秒）；`RedisStore` 是一次
往返（同机房 0.2–1ms）。对照一次 500ms–30s 的 LLM 调用，占比 < 0.2%。
**两种形状的延迟都是噪声**；优先第一种是为了少一个活动部件，不是为了延迟。

### 4.2 账本：门户数据库

用户、凭据、邮箱验证态、余额、流水必须落在**有事务的数据库**（SQLite 单机 /
Postgres），不进配置文档。理由：可变、带密、高写入，且**余额变更必须在事务里**
——充值与扣减竞态不能丢钱。

配置文档里只留网关认识的那部分：
`ApiKey{key_hash, user_id, allowed_models, rate_limit, disabled, expires_at}`。

### 4.3 对账：读闸，不读遥测

门户**不依赖有损的 usage events 对账**，而是读网关那个据以拒绝的计数器——
那是权威值。为此 Admin API 需要一个**只读**的"剩余额度"接口。

这同时消解了 §3.1 的精确性问题：账本的耗用 = 授予总额 − 网关报告的剩余额度。

## 5. 组件与边界

### 5.1 分进程，不分角色

`aisix-portal`（新）与 `aisix-console`（现有，收敛为纯管理端）：**两个二进制、
两个监听、两套会话**。

理由：共享口令的全权管理端不能同时服务陌生人。角色判断错一次就是全量泄漏；
进程分开后，门户里**根本不存在配置编辑的代码路径**。管理端继续只在受限网络暴露。

### 5.2 计量隔离是硬边界

门户**不暴露 PromQL**。改为具名参数化查询，`user_id` **从会话注入，永不从
请求体读**。这一条不是"记得加过滤"，是端点形状本身不接受用户提供的查询。

现有 `/api/metrics` 的 `aisix_` 前缀闸对跨租户读取无效（§2 缺口 6），门户不复用它。

### 5.3 密钥写入路径

自助多租户要求每个密钥独立写入，因此走 etcd（managed 模式）而非整份
`resources.yaml` 重写。这需要 Admin API 长出写接口（§2 缺口 4）。

**替代方案与否决理由**：门户直写 etcd 可行，但会引入第二个 etcd 写入者，
与仓库既有的"控制面是唯一写入者、且写入前校验"的约定冲突，且绕过资源校验。

## 6. 安全边界

1. **租户隔离**：任何按用户维度返回数据的端点，用户标识只来自会话。
2. **凭据**：明文密钥只在铸造响应里出现一次，落库只存散列（现有
   `api_mint_key` 已是此形状）。
3. **注册滥用**：预付模型下陌生人拿不到免费推理，滥用面主要是注册垃圾与
   邮箱验证轰炸，按常规限流处理。
4. **管理端可达性**：管理端与门户分离部署，管理端不对公网开放。
5. **越权充值**：充值与额度发放是记账操作，必须有审计流水（谁、何时、多少、
   凭什么）。

## 7. 分期

本设计跨多个子系统，**不应作为单一计划执行**。建议拆成四期，每期自身可用：

- **一期 · 身份与门户骨架**：用户表、注册/登录/会话、门户进程、只读的
  "我的用量"（具名查询）。额度由管理员在管理端手工发放。**不动网关。**

  一期没有累计闸，因此**闸由控制环临时充当**：门户轮询消费，扣减账本余额，
  归零即把该用户的密钥置 `disabled: true`（鉴权处已强制执行，§2）。窗口型
  `max_spend_micro_usd` 在此**只作单日透支兜底**，不作余额——它会随窗口刷新，
  拿它表达余额就是每天续杯（§2 缺口 3）。

  一期须明确接受两项限制，三期消除：
  - 对账只能读 Prometheus（三个有损来源里最不坏的一个），账目有漂移，
    §4.3 的"读闸"在这一期尚不可用；
  - 超支上界 = 轮询周期内的消费 + 在途，按 §3.2 由速率反推压住。
- **二期 · 密钥自助**：Admin API 写接口；门户铸密钥并写入 etcd；密钥列表/吊销。
- **三期 · 累计额度闸**：网关侧不重置的累计扣减计数器；Admin API 剩余额度只读
  接口；门户账本按 §4.3 对账。**这一期动网关。**
- **四期 · 自助充值**：接入支付。在此之前额度只能由管理员发放。

## 8. 未决问题

1. **支付渠道未定**。四期需要，一至三期不需要。账本的 credit 操作应设计成
   来源可插拔（`admin_grant` / `payment`），使四期不必重写账本。
2. **一期用哪种数据库**。SQLite 够单机；若一开始就要多实例门户则需 Postgres。
   取决于部署形态，未定。
3. **累计计数器的存储形状**（三期）。`RateStore` 现有接口是窗口语义，
   累计扣减是否复用 `acquire`/`commit` 还是另开方法，需在三期设计时定。
4. **标准模式（`resources_file`）是否支持自助**。二期走 etcd；文件模式下
   多租户自助是否支持，未定。

## 9. 评审要点

最该被否掉的三处：

- **分两个进程**（§5.1）——代价是多一个二进制与一套部署。
- **Admin API 补写接口**（§5.3）——这是本仓库的改动，不是纯"密钥管理侧"。
- **三期动网关**（§4.1）——虽然不动转发路径，但动了准入与存储。
