## H-01 — One metric emit bypasses the label-bounding chokepoint

**Where:** `crates/aisix-proxy/src/chat.rs:299`

`Metrics::set_rate_limit_remaining` is called directly with `model_name`,
which is `req.model.clone()` (`chat.rs:129`) — the raw caller-supplied
string. That value becomes the `model` label on
`aisix_ratelimit_remaining_requests` and `..._tokens`.

Every other emit in the same handler routes through
`request_metrics::record` / `record_usage`, which exist precisely to collapse
the raw string through `usage_attr::metric_model_label_pair`. That module's
own doc comment states the contract this call site breaks:

```
crates/aisix-proxy/src/request_metrics.rs:150
    /// MUST be bounded: a name that already resolved against the snapshot,
    /// or `usage_attr::metric_model_label()` output on any path that can
    /// fire before resolution. The raw client-supplied `model` is
    /// attacker-controlled cardinality (#451).
```

`AGENTS.md` also names this shape directly: *"Emit the request metrics
through `request_metrics::record` and nothing else."*

**Impact.** With a wildcard model row configured (`display_name: "openai/*"`),
a caller mints arbitrary concrete model names that authenticate and succeed.
Each distinct `(api_key_id, model)` pair permanently registers two new
Prometheus series. `PrometheusBuilder::new()` is built without
`idle_timeout` (`crates/aisix-obs/src/metrics.rs:722`), so nothing is ever
evicted: the registry grows without bound and the `/metrics` scrape grows
with it. This is the #959 bug class already fixed elsewhere in the repo,
left on the one emit that never went through the chokepoint.

**Evidence:**

```
crates/aisix-proxy/src/chat.rs:299     state.metrics.set_rate_limit_remaining(&api_key_id, &model_name, …)
crates/aisix-proxy/src/chat.rs:129     let model_name = req.model.clone();   // caller-supplied
crates/aisix-obs/src/metrics.rs:1804   k.label(model);  →  "model" => model.to_string()
crates/aisix-obs/src/metrics.rs:722    PrometheusBuilder::new()              // no .idle_timeout(...)
```

`set_rate_limit_remaining` has exactly one call site, so the fix is local.

**Suggested fix.** The request's snapshot is already loaded one line away;
bound the label at the call site:

```rust
// crates/aisix-proxy/src/chat.rs — inside the `if let Some(rl_status) = …` block
let (bounded_model, _) = crate::usage_attr::metric_model_label_pair(
    &snapshot,
    &model_name,
    success.upstream_model.as_str(),
);
state.metrics.set_rate_limit_remaining(
    &api_key_id,
    bounded_model.as_ref(),
    rl_status.rpm_remaining(),
    rl_status.tpm_remaining(),
);
```

Better, and it closes L-11 at the same time: move the peek-inject-emit
triple into one `request_metrics`-side helper that does the bounding
internally, so no future call site can reintroduce this.

Defence in depth worth adding regardless — an idle timeout on the recorder,
so a future unbounded dimension degrades into stale-series churn instead of
permanent growth:

```rust
// crates/aisix-obs/src/metrics.rs:722
// `MetricKindMask` is re-exported by metrics-exporter-prometheus and is
// not imported here yet — add it to the existing `use` at the top.
let recorder = PrometheusBuilder::new()
    .idle_timeout(MetricKindMask::GAUGE, Some(Duration::from_secs(15 * 60)))
    .set_buckets_for_metric(…)
```

Scope this deliberately: `GAUGE` only. Masking counters or histograms would
let a low-traffic-but-real series disappear from the scrape and read as
"no traffic", which is the failure mode `AGENTS.md` warns about for metrics.

**Test to add.** An e2e that drives `/v1/chat/completions` twice against a
wildcard row with two different concrete aliases, then asserts
`GET /metrics` contains exactly one `aisix_ratelimit_remaining_requests`
series for that key, labelled with the wildcard row's `display_name`.
Per `AGENTS.md`, a metric family is only shipped when an e2e asserts it in
`GET /metrics` after real traffic — the same standard applies to asserting
one is *not* over-emitted.

## M-02 — IPv4-mapped addresses defeat every CIDR gate on a dual-stack listener

**Where:** `crates/aisix-proxy/src/client_ip.rs:175`,
`crates/aisix-core/src/models/model.rs:391-398`

Nothing in the repo canonicalizes IPv4-mapped IPv6 addresses. When the proxy
binds `[::]:3000` — routine under Docker and Kubernetes, and permitted since
`proxy.addr` is a free-form socket address — an IPv4 client's peer address
arrives as `::ffff:10.0.0.1`, and `IpNet::contains` returns `false` for an
IPv4 network against an IPv6 address.

**Impact.** Two gates fail silently, in opposite directions:

- `proxy.real_ip.trusted` never matches, so `resolve_client_ip` returns
  early at *"an untrusted peer IS the client"*. The forwarded header is
  ignored and every caller is attributed to the load balancer's address —
  in access logs, usage events, and any `allowed_cidrs` decision downstream.
- `Model.allowed_cidrs` never matches, so **legitimate traffic is rejected
  with 403** (`ProxyError::ModelIpRestricted`).

The same configuration works on `0.0.0.0` and breaks on `[::]` with no error
or warning anywhere.

**Evidence.** Runnable, against this workspace's own `ipnet` version:

```rust
use ipnet::IpNet;
use std::net::IpAddr;
fn main() {
    let net: IpNet = "10.0.0.0/8".parse().unwrap();
    let mapped: IpAddr = "::ffff:10.0.0.1".parse().unwrap();
    let plain: IpAddr = "10.0.0.1".parse().unwrap();
    println!("{}", net.contains(&plain));                 // true
    println!("{}", net.contains(&mapped));                // false
    println!("{}", "0.0.0.0/0".parse::<IpNet>().unwrap().contains(&mapped)); // false
    println!("{}", net.contains(&mapped.to_canonical())); // true
}
```

```
v4 cidr contains plain v4      = true
v4 cidr contains v4-mapped v6  = false
0.0.0.0/0 contains v4-mapped   = false
mapped.to_canonical()          = 10.0.0.1
v4 cidr contains canonicalized = true
```

**Suggested fix.** Normalize at the two entry points. `IpAddr::to_canonical`
is stable and a no-op for genuine IPv6.

```rust
// crates/aisix-proxy/src/client_ip.rs — source_ip_from_parts
.map(|ci| ci.0.ip().to_canonical())
```

```rust
// crates/aisix-proxy/src/client_ip.rs — parse_forwarded_token
// each returned address, e.g.:
if let Ok(ip) = tok.parse::<IpAddr>() {
    return Some(ip.to_canonical());
}
```

```rust
// crates/aisix-core/src/models/model.rs — ip_allowed
let ip: std::net::IpAddr = match source_ip.parse() {
    Ok(ip) => ip,
    Err(_) => return false,
};
let ip = ip.to_canonical();
```

**Test to add.** Extend the existing `ip_allowed_matrix` test with
`assert!(v4.ip_allowed("::ffff:10.1.2.3"))`, and add a `resolve_client_ip`
case whose peer is `::ffff:` a trusted-CIDR address, asserting the forwarded
header is honoured.

## M-03 — Cache entries addressed by a 64-bit, version-unstable hash with no key verification

**Where:** `crates/aisix-cache/src/key.rs:92`,
`crates/aisix-cache/src/memory.rs:33`

`CacheKey::fingerprint` hashes with
`std::collections::hash_map::DefaultHasher` and formats the resulting `u64`
as the backend's lookup key. Neither backend stores the originating key —
`MemoryCache` is `MokaCache<String, Entry>` where `Entry` is
`{ response, ttl }` — so a lookup that lands on an entry serves it. There is
no full-key comparison on hit.

**Impact, two distinct problems:**

1. **Collision serves the wrong tenant's response.** Under `scope: env`
   (no `scope_api_key` segment in the fingerprint) entries are shared across
   callers, so a 64-bit collision means one caller receives another's cached
   completion. The existing comment reasons about accidental collisions over
   "the bounded request space", which holds for the 10k-entry in-memory
   default; it does not hold for a shared, persistent Redis cache at scale,
   where collision probability grows quadratically with entry count.

2. **Version instability, which is the likelier operational failure.** Rust
   documents `DefaultHasher`'s algorithm as unspecified and not guaranteed
   across releases. The Redis backend is shared across replicas and
   persists. During a rolling upgrade that crosses a change in that
   implementation, replicas compute *different* fingerprints for identical
   requests: hit rate collapses, and the semantic layer's
   `scope_fingerprint` partitions the same way — silently, with no metric
   distinguishing it from a cold cache.

**Evidence:**

```
crates/aisix-cache/src/key.rs:92     DefaultHasher::new() → format!("{:016x}", h.finish())
crates/aisix-cache/src/memory.rs:33  inner: MokaCache<String, Entry>   // key is the digest only
crates/aisix-cache/src/key.rs:11     "a stronger hash would be a single-line drop-in if we ever need it"
```

**Suggested fix.** Take the drop-in the comment already anticipates. A fixed
128-bit hash removes both problems at once — it is version-stable by
construction and puts collision probability out of reach:

```rust
// crates/aisix-cache/src/key.rs
fn digest(&self, include_messages: bool) -> String {
    let mut h = blake3::Hasher::new();
    // feed the same field order hash_scope/Hash use today, via a
    // length-prefixed writer so no two field tuples can alias
    …
    hex::encode(&h.finalize().as_bytes()[..16])   // 128 bits
}
```

If adding a dependency is unwanted, `SipHasher13::new_with_keys(K1, K2)`
with constants pinned in this file is version-stable and needs no new crate;
it stays 64-bit, so it fixes (2) but not (1).

Closing (1) completely means storing the canonical key beside the value and
comparing on hit — a larger change, worth it only if `scope: env` sharing
across tenants is a supported posture rather than a convenience.

**Note for the CP side.** Whichever is chosen, the fingerprint format
changes, so every existing Redis entry becomes unreachable at deploy. That
is a cache flush, not a correctness event, but it belongs in the release
notes.

## M-04 — Every dispatch deep-copies the `Model`/`ProviderKey` it already holds behind an `Arc`

**Where:** ten dispatch sites, plus `routing.rs:823` and `routing.rs:871`

`BridgeContext` is already declared to take `Arc<Model>` and
`Arc<ProviderKey>` (`crates/aisix-gateway/src/bridge.rs:97-100`) — the design
is right. But `ResourceEntry<T>` holds `value: T` by value
(`crates/aisix-core/src/resource.rs:45`), so every call site clones the value
out of the snapshot's `Arc<ResourceEntry<T>>` and wraps it in a *fresh*
`Arc`. The refcount buys nothing. On top of that,
`resolve_attempt_models` clones the same `Model` a second time when building
the attempt list.

**Measured cost** (this machine, `--release`, `opt-level = 3`):

```
size_of::<Model>()       = 760 bytes
size_of::<ProviderKey>() = 496 bytes

direct model                 clone:  42.8 ns/op
routing group (8 targets)     clone: 349.1 ns/op
ProviderKey                  clone:  74.6 ns/op
```

A direct chat request therefore pays ~160 ns and roughly a dozen heap
allocations in avoidable copying (`Model` twice + `ProviderKey` once). A
routing group pays closer to a microsecond, because `eligible_targets` and
the `..routing.clone()` that immediately discards its own `targets` field
each copy the full target vector as well (L-09). A semantic router — whose
`Model` carries every route's example utterances — is worse again, and scales
with the size of the operator's route config.

This lands directly on the allocator pressure the jemalloc switch was made to
reduce (`main.rs`: allocator time "~15% of request CPU (glibc malloc) to
~6%"). Cutting allocation count is the lever on the remaining 6%.

**Evidence:**

```
crates/aisix-proxy/src/chat.rs:1544,2677     Arc::new(model.clone()) / Arc::new(pk_entry.value.clone())
crates/aisix-proxy/src/messages.rs:1949      same
crates/aisix-proxy/src/responses.rs:2195     same
crates/aisix-proxy/src/completions.rs:497    same
crates/aisix-proxy/src/embeddings.rs:447     same
crates/aisix-proxy/src/images.rs:391         same
crates/aisix-proxy/src/semantic.rs:439       same
crates/aisix-proxy/src/ensemble.rs:140       same
crates/aisix-proxy/src/background.rs:141     same
crates/aisix-proxy/src/routing.rs:823        AttemptModel { model: virtual_model.clone() }
crates/aisix-proxy/src/routing.rs:871        AttemptModel { model: target_entry.value.clone() }
```

**Suggested fix.** One change at the root makes all eleven sites cheap:

```rust
// crates/aisix-core/src/resource.rs
pub struct ResourceEntry<T> {
    pub id: String,
    pub value: std::sync::Arc<T>,
    pub revision: i64,
}

impl<T> ResourceEntry<T> {
    pub fn new(id: impl Into<String>, value: T, revision: i64) -> Self {
        Self { id: id.into(), value: std::sync::Arc::new(value), revision }
    }
}

impl<T> Deref for ResourceEntry<T> {
    type Target = T;
    fn deref(&self) -> &Self::Target { &self.value }
}
```

The existing `Deref` keeps every reader compiling unchanged, and each
dispatch site becomes:

```rust
let mut ctx = crate::dispatch::bridge_ctx(
    request_id,
    &attempt.id,
    Arc::clone(&attempt.model),          // was Arc::new(model.clone())
    &pk_entry.id,
    Arc::clone(&pk_entry.value),         // was Arc::new(pk_entry.value.clone())
    Some(client),
);
```

with `AttemptModel.model` becoming `Arc<Model>`. `Serialize`/`Deserialize`
pass through `Arc<T>` transparently, so the etcd loader and the snapshot
cache are unaffected. The one thing to check is any site that mutates
`entry.value` in place — the admin store's update path — which becomes
`Arc::make_mut`.

**Sequencing note.** This is mechanical but touches many files. It is worth
landing on its own, ahead of L-09, since L-09's `Cow` change reads much more
cleanly once `AttemptModel` is already `Arc`-based.

## M-05 — Default rate-limit backend never evicts a bucket

**Where:** `crates/aisix-ratelimit/src/store/local.rs:51`

```
states: DashMap<String, Arc<Mutex<KeyState>>>
```

There is no eviction anywhere in the crate:

```
$ grep -rnE 'retain|remove\(|evict|reap|prune|shrink' crates/aisix-ratelimit/src
(no matches)
```

Keys accumulate across every API key, model, MCP server, and policy bucket
tuple the process has ever seen — including rows deleted from the control
plane hours earlier. Each entry holds six `FixedWindowCounter`s plus its key
string.

**Impact.** Bounded by config cardinality rather than by traffic, so this is
a slow leak, not a DoS. I confirmed the bucket keys are all
config-derived — `policy:v2:<id>:<dim>=<value>` resolves `GroupByDimension::Model`
to `model_rl.entry_id`, the resolved row's id, not the caller-minted
string — so there is no caller-controlled cardinality here. But a large
multi-tenant deployment with key rotation accumulates buckets monotonically
for the process lifetime, and the only remedy is a restart.

**Suggested fix.** Stamp last-touched and reap from the upkeep task that
already drives `Metrics::run_upkeep`:

```rust
// crates/aisix-ratelimit/src/store/local.rs
struct KeyState {
    …
    last_touched: u64,        // unix secs, written under the existing mutex
}

impl<C: Clock> LocalStore<C> {
    /// Drop buckets idle for longer than the widest window (one day), so
    /// state for deleted keys and models does not accrue for the process
    /// lifetime. Called from the server's periodic upkeep task.
    pub fn reap(&self, idle_for: Duration) {
        let cutoff = self.clock.unix_secs().saturating_sub(idle_for.as_secs());
        self.states.retain(|_, s| {
            let s = s.lock();
            s.in_flight > 0 || s.last_touched >= cutoff
        });
    }
}
```

The `in_flight > 0` guard matters: a bucket with a live concurrency permit
must never be dropped, or the `Drop`-based release decrements a bucket that
no longer exists and the next reservation sees a fresh zero.

Expose it through `Limiter` so `RedisStore` gets a no-op impl and the
server calls one method regardless of backend.

## M-06 — Config apply is per event, not per batch

**Where:** `crates/aisix-etcd/src/supervisor.rs:1162-1166`, `:734`

The module doc states the design:

```
crates/aisix-etcd/src/supervisor.rs:14
//! The apply step is *copy-on-write* per batch: we clone the current
//! snapshot into a new one, mutate, and `store` it.
```

The implementation is per **event**:

```rust
// :1162
Some(Ok(WatchEvent::Put(raw)))       => { self.apply_put(&raw); }
Some(Ok(WatchEvent::Delete{ key, ..})) => { self.apply_delete(&key); }
```

and each call does a full deep copy of all fourteen `ResourceTable`s — both
the `by_id` and `by_name` indices, every key `String`:

```rust
// :734
self.handle.rcu(|current| {
    let new = clone_snapshot(current);
    merge_snapshot(&new, &tiny);
    new
});
```

Each event additionally re-serializes the snapshot cache to disk
(`flush_cache`) while holding `apply_transaction`.

**Impact.** Cost is O(total resources) per single write. A bulk control-plane
operation — rotating a thousand keys, seeding an environment, a large
migration — becomes O(N²) work with a matching allocation spike and N cache
flushes. Correct at every size; quietly expensive at large ones. The RCU
retry loop also re-runs `clone_snapshot` on CAS contention, so concurrent
applies multiply the cost further.

**Suggested fix.** Coalesce the watch stream, which the `tiny`-snapshot
merge design already supports — `merge_snapshot` takes an arbitrary delta,
so batching is a change to the *caller*, not to the merge:

```rust
// crates/aisix-etcd/src/supervisor.rs — watch loop
let mut batch: Vec<WatchEvent> = Vec::new();
loop {
    tokio::select! {
        ev = stream.next() => match ev {
            Some(Ok(e)) => {
                batch.push(e);
                // Drain whatever else already arrived, bounded so a
                // hot writer cannot starve the apply.
                while batch.len() < MAX_APPLY_BATCH {
                    match stream.next().now_or_never() {
                        Some(Some(Ok(e))) => batch.push(e),
                        _ => break,
                    }
                }
                self.apply_batch(&batch);   // one rcu + one flush_cache
                batch.clear();
            }
            …
        }
    }
}
```

`apply_batch` builds one `tiny` snapshot from every Put in the batch, applies
the Deletes into the same cloned snapshot, and does a single `rcu` and a
single `flush_cache`. Per-event rejection handling, `capture_last_good`, and
the partial-compat bookkeeping stay exactly as they are — they operate on
individual entries and need no change.

If batching is judged not worth the risk, the module doc at `:14` should be
corrected to describe the per-event reality, so the next reader does not
assume a batching guarantee that isn't there.

## L-07 — Global `Mutex` on the guardrail-index fast path

**Where:** `crates/aisix-guardrails/src/build.rs:1104`, `:833`

`LiveGuardrailIndex::current()` takes a process-wide `std::sync::Mutex` on
every request just to compare a version number and clone an `Arc`:

```rust
// :1151
let cache = self.cache.lock().expect("LiveGuardrailIndex mutex poisoned");
if cache.last_version >= view.version {
    return Arc::clone(&cache.index);
}
```

There is a second such cache in the same crate (`:833`). On a 192-thread
thread-per-core deployment this is the one place the otherwise lock-free read
path serializes. The hold is very short, so it is a scaling ceiling rather
than a stall — and `resolve()` already short-circuits an empty index, so
guardrail-free deployments still pay the lock.

**Suggested fix.** `ArcSwap` makes the hit path a single atomic load, matching
how `SnapshotHandle` already publishes config. The existing comment — *"A
concurrent rebuild (rare) is harmless — both produce equivalent indexes from
the same snapshot version"* — means the swap needs no extra synchronization:

```rust
pub struct LiveGuardrailIndex {
    …
    cache: arc_swap::ArcSwap<IndexCache>,
}

fn current(&self) -> Arc<GuardrailIndex> {
    let view = self.snapshot.load_versioned();
    let cached = self.cache.load();
    if cached.last_version >= view.version {
        return Arc::clone(&cached.index);
    }
    let index = Arc::new(build_index_from_snapshot(…));
    // Last writer wins; both writers built from the same version.
    self.cache.store(Arc::new(IndexCache { last_version: view.version, index: index.clone() }));
    index
}
```

`arc-swap = "1.7"` is already declared in the workspace
(`Cargo.toml:100`), but `aisix-guardrails` does not currently depend on it —
this needs `arc-swap.workspace = true` added to
`crates/aisix-guardrails/Cargo.toml`, the same line `aisix-core` already has.

## L-08 — `allowed_cidrs` re-parsed from strings on every request, per target

**Where:** `crates/aisix-core/src/models/model.rs:397`

```rust
ranges.iter()
    .filter_map(|cidr| cidr.parse::<ipnet::IpNet>().ok())
    .any(|net| net.contains(&ip))
```

`routing.rs:797` calls this once per routing target, so a group of eight
multiplies the parsing. `ResolvedRealIp` already demonstrates the intended
pattern, and says so:

```
crates/aisix-proxy/src/client_ip.rs:24
/// Pre-parsed `proxy.real_ip` config carried on [`ProxyState`] so the
/// per-request extractor doesn't re-parse CIDRs on the hot path.
```

A second issue in the same three lines: `filter_map(…ok())` silently skips a
malformed CIDR, so a typo narrows the allowlist with no signal — a
fail-closed outcome, but an invisible one, which is the shape
`config_status.rs` exists to make visible everywhere else.

**Suggested fix.** Parse once when the row is loaded and keep the raw strings
for round-tripping:

```rust
// crates/aisix-core/src/models/model.rs
#[serde(skip)]
allowed_cidrs_parsed: std::sync::OnceLock<Vec<ipnet::IpNet>>,

pub fn ip_allowed(&self, source_ip: &str) -> bool {
    let ranges = match self.allowed_cidrs.as_deref() {
        Some(r) if !r.is_empty() => r,
        _ => return true,
    };
    let Ok(ip) = source_ip.parse::<std::net::IpAddr>() else { return false };
    let ip = ip.to_canonical();                     // see M-02
    let nets = self.allowed_cidrs_parsed.get_or_init(|| {
        ranges.iter().filter_map(|c| c.parse().ok()).collect()
    });
    nets.iter().any(|net| net.contains(&ip))
}
```

and reject an unparseable CIDR at load, in the same validator that rejects
every other malformed field, so the row surfaces through the existing
rejection channel instead of degrading.

## L-09 — Routing resolution copies the target list twice and discards one copy

**Where:** `crates/aisix-proxy/src/routing.rs:830`, `:850`, `:538`

```rust
// :830
let eligible = eligible_targets(&routing.targets, req.tags);
// :850
let filtered_routing = Routing { targets: eligible, ..routing.clone() };
```

`eligible_targets` returns owned clones even when no target is tagged and
nothing is filtered (`:538  return targets.to_vec();`). Then
`routing.clone()` copies the entire `Routing` *including its own `targets`
vector*, which is immediately overwritten by `eligible` and dropped.

So a routing request with N targets copies N `RoutingTarget`s twice — each
carrying a model name `String` and a tags `Vec<String>` — and throws one copy
away. `pick_targets` only reads `strategy`, `sticky_or_default()`, and
`max_fallbacks_or_default()` off the `Routing` it is handed.

**Suggested fix.** Borrow in the common case and stop rebuilding `Routing`:

```rust
fn eligible_targets<'a>(
    targets: &'a [RoutingTarget],
    request_tags: &[String],
) -> std::borrow::Cow<'a, [RoutingTarget]> {
    if !targets.iter().any(RoutingTarget::has_tags) {
        return std::borrow::Cow::Borrowed(targets);
    }
    …
}
```

and change `pick_targets` to take `(&Routing, &[RoutingTarget])` so the
filtered slice is passed alongside the config rather than spliced into a
clone of it. `targets_allowed_for_ip` then takes and returns the same `Cow`,
staying borrowed whenever no target is excluded — which is the default.

## L-10 — `/v1/messages` runs the budget check twice, and the two paths differ

**Where:** `crates/aisix-proxy/src/messages.rs:652` and `:655`

```rust
// :652
let mut reservation = Some(crate::quota::enforce(state, snapshot, auth, Some(&model_rl)).await?);
// :655
let budget_decision = state.budgets.check(&auth.entry.id).await;
```

`quota::enforce` already calls `check_budget` internally
(`crates/aisix-proxy/src/quota.rs:462`). Both hit the 5-second decision cache
so the runtime cost is trivial, but the two are **not** interchangeable:
`check_budget` also refreshes the budget gauges
(`set_budget_gauges` / `clear_budget_gauges`), and the inline block at `:655`
does not. A future edit to one will silently not apply to the other.

`chat.rs` is the deliberate exception — it uses `enforce_rate_limit` and owns
the budget check itself, with a comment saying so. `messages.rs` appears to
have inherited the chat shape on top of the shared gate.

**Suggested fix.** Delete `:655-663`. `quota::enforce` already produces the
identical `ProxyError::BudgetExceeded` and additionally syncs the gauges.

## L-11 — `x-ratelimit-*` response headers exist on `/v1/chat/completions` only

**Where:** `crates/aisix-proxy/src/render.rs:252`, called from
`crates/aisix-proxy/src/chat.rs:298` — the only call site.

```
$ grep -rn 'inject_ratelimit_headers' crates/aisix-proxy/src/*.rs
render.rs:252   pub fn inject_ratelimit_headers(…)
chat.rs:298     crate::render::inject_ratelimit_headers(&mut success.response, &rl_status);
```

The OpenAI and Anthropic SDKs read these headers to schedule backoff. A
client driving `/v1/responses` (Codex), `/v1/messages` (Claude Code),
`/v1/embeddings`, or `/v1/completions` gets no window state and backs off
blindly into the gateway's 429s. Nothing errors — the feature is simply
absent on the siblings, which is the family-drift shape `AGENTS.md` calls
out: *"a gap on the unfixed siblings is SILENT."*

**Suggested fix.** One helper, called from each endpoint's success tail,
doing the peek, the header injection, and the (bounded — see H-01) gauge
emit together:

```rust
// crates/aisix-proxy/src/request_metrics.rs
/// Peek the caller's current window and both publish it to the client

/// the header without the metric, or the metric with an unbounded label.
pub(crate) async fn publish_rate_limit_window(
    state: &ProxyState,
    snapshot: &aisix_core::AisixSnapshot,
    auth: &AuthenticatedKey,
    requested_model: &str,
    upstream_model: &str,
    response: &mut Response,
) { … }
```

Then wire it into chat, messages, responses, completions, embeddings, rerank,
and images in the same change — or state explicitly which sibling is deferred
and file the follow-up, per the lockstep rule.

## L-12 — Semantic cache lookup is a linear cosine scan under a shard guard

**Where:** `crates/aisix-cache/src/semantic.rs:156`, `:166`

```rust
let Some(policy) = self.policies.get(policy_id) else { return Ok(None) };   // :156 — guard
…
for entry in &policy.entries {                                             // :166
    let similarity = cosine_similarity(embedding, &entry.embedding);
```

The `DashMap` read guard is held for the whole scan. With `max_entries` in
the thousands and typical embedding widths, that is millions of float
operations per request, serialized against any concurrent `store` on the same
policy — and `store` calls `self.policies.retain(…)`, which needs every
shard.

Fine at small `max_entries`; it degrades with the product of cache size and
request rate. `cosine_similarity` also recomputes both norms on every
comparison, though only the query's norm changes per request.

**Suggested fix.** Two independent improvements:

```rust
// 1. Release the guard before scanning.
let entries: Vec<Arc<SemanticEntry>> = {
    let Some(policy) = self.policies.get(policy_id) else { return Ok(None) };
    if policy.generation != generation { return Ok(None) }
    policy.entries.iter().cloned().collect()
};   // guard dropped here
```

(which means `PolicyEntries.entries` becomes `VecDeque<Arc<SemanticEntry>>` —
the clone is then N refcount bumps, not N deep copies.)

```rust
// 2. Normalize at store time so the scan is a dot product.
//    Store `embedding` pre-normalized; then similarity is just:
let similarity = dot(embedding_normalized, &entry.embedding);
```

Normalizing the query once per request and each entry once at store time
removes both `sqrt` calls and both norm loops from the inner comparison.

## N-14 — MCP connect-timeout test fails behind any `HTTP_PROXY` (not a product defect)

**Where:** `crates/aisix-mcp/src/bridge.rs:806`

This is the single test failure in the suite. It is environmental.

```

3282 passed · 1 failed
dial was not bounded by connect_timeout: took 12.001798483s
```

The test dials `http://203.0.113.1:81/mcp` (TEST-NET-3, black-holed) and
asserts the dial is bounded by `upstream.connect_timeout_ms` (5 s default)
rather than the 12 s outer `upstream.timeout`. reqwest honours `HTTP_PROXY`
by default, so the client instead connects to the proxy — which accepts

**Suggested fix.** Make the test independent of ambient proxy configuration.

```rust
    // …build the transport with a no_proxy() client, or:
    // #[cfg_attr(…)] skip when a proxy env var is set, with a logged reason.

```

A `no_proxy()` client in the test is preferable to skipping — a skip that
silently activates in every corporate-proxy CI is how the original bug
(rmcp's missing connect timeout) would come back unnoticed.

## Architecture observations

### Handler families are held in lockstep by discipline, not by structure

The lockstep rule is enforced wherever a real chokepoint exists —
`resolve_attempt_models`, `quota::enforce`, `request_metrics::record`,
`usage_attr`. I checked budget enforcement, IP gates, guardrail resolution,
and metric label bounding across all fifteen handlers and found them
consistently wired. Two things I initially suspected were gaps turned out to
be correct: the cp-api budget gate reaches every endpoint through
`quota::enforce` (chat is the documented exception), and both
`request_metrics::record` and `record_usage` bound the model label at the
chokepoint.

Where a chokepoint is missing, the drift is exactly where you would predict
it. H-01 and L-11 are both emits that call `Metrics` / `render` directly
instead of going through a shared function. **The remaining gaps are
precisely the call sites that bypass an existing chokepoint** — which makes
them mechanically findable rather than a matter of vigilance. A lint or a
test that asserts `Metrics::set_*` / `Metrics::record_*` has no caller
outside `request_metrics` would convert this whole class into a build
failure.

### Four near-identical dispatch loops

`chat.rs`, `messages.rs`, `responses.rs`, and `count_tokens.rs` each carry
their own copy of the target walk: reserve the per-target quota, resolve the
bridge, connect, stage the attempt record, classify retryability, back off,
mark cooldown, fail over, and finally surface either the last quota rejection
or the last bridge error. The bodies differ only in wire shape.

`chat::dispatch` spans lines 1165–3207 — over 2,000 lines in one function —
with `build_sse_stream` adding ~930 and `lib.rs` reaching 9,691. These are
the files where the next silent divergence will appear, and where a
reviewer's attention runs out first.

A generic `dispatch_targets(attempts, per_attempt_fn)` driving the shared
loop, with each endpoint supplying only its connect-and-parse closure, would
collapse most of it. Large refactor, real risk — but the four copies are the
structural reason the lockstep rule needs restating in three separate
documents.

### What holds up well

- **Telemetry on the cancellation path.** `CompleteOnDrop` fires end-of-stream
  accounting whether the stream completes or the client disconnects, and the
  `delivered == 0` gate zeroes completion-side counters so an abandoned
  stream is not billed for output nobody received. A genuinely hard case,
  handled correctly.
- **Failure modes are explicit.** A cache policy asking for a Redis backend
  that does not exist gets no caching plus a warn-once line, never a silent
  fallback to node-local memory with different sharing semantics. That
  instinct — degrade visibly, never plausibly — recurs throughout.
- **Performance work is already past the obvious tier.** Fat LTO with one
  codegen unit, three-phase PGO in the Dockerfile, jemalloc with a
  runtime-enabled background purge thread, thread-per-core serving on
  `SO_REUSEPORT` with per-worker connection pools, lock-free snapshot reads,
  worker-thread-local metric handle caches. The performance findings above
  are the *next* tier — per-request allocation and lock contention — not
  first-pass oversights.
- **The comments carry the reasoning.** Nearly every non-obvious branch
  records why it exists and which issue it closed. That is what made this
  audit tractable at 204k lines, and it is why the findings are narrow.
